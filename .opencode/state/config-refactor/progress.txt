# Progress Log

PRD: config-refactor
Started: 2026-02-18

## Codebase Patterns

- Config types live in `crates/core/src/config/mod.rs`, re-exported via `crates/core/src/lib.rs`
- Crate dir is `crates/core/` (not `crates/actup-core/` as AGENTS.md suggests)
- Enums use `#[serde(rename_all = "lowercase")]` for TOML/JSON serialization
- Tests in same file via `#[cfg(test)] mod tests`, use `#[allow(clippy::unwrap_used)]`
- `serde_json` + `toml` available as dev-deps for round-trip tests
- `deny_unknown_fields` used on `FetchSettings` and `HostConfig`
- `Hash` derive needed on `HostKind` for use as `HashMap` key in later tasks
- Registration types in `config/registration.rs` submodule, re-exported from `lib.rs`
- `Registration` uses `fn` pointer fields (`infer_api_base`, `create`); needs manual `Debug` impl with `finish_non_exhaustive()`
- CLI `build_registry()` in `crates/actup/src/main.rs` — main consumer of config provider fields; calls `available_registrations()` for early preset validation
- `available_registrations()` in `crates/actup/src/main.rs` — feature-gated provider assembly; can't live in `actup-providers` due to circular deps
- Validation functions in `config/validation.rs` submodule, re-exported from `lib.rs`
- Validation errors use `Error::InvalidConfig { path: context, reason }` — `path` field doubles as context string (e.g. `"hosts"`, `"default_host"`, `"host \"ghe.corp.com\""`)
- `validate_api_base` returns normalized `String` (trailing `/` stripped) — caller should use returned value
- Config display in `crates/actup/src/commands/config.rs` — human-readable config output
- Example configs in `examples/` — must be kept in sync with config struct changes
- `Config` has `#[serde(default)]` on the struct, so all new fields must either have `Default` or be `Option`
- Resolution logic in `config/resolution.rs` submodule — `effective_host()` is the entry point for hostname-to-`ProviderConfig` resolution; `resolve_default_host()` handles `default_host` fallback to `"github.com"` preset
- `effective_host()` takes `&Config`, `&[&Registration]`, and `&FetchSettings` — re-exported from `actup_core`; CLI will call it per-host in `build_registry()`

## Task - validation

- Added `config/validation.rs` submodule with three public validation functions
- `validate_hostname(hostname, context)`: rejects empty, uppercase, schemes, paths, ports, whitespace
- `validate_api_base(api_base, context)`: requires `http://` or `https://` scheme, rejects `?`/`#`, strips trailing `/`, returns normalized `String`
- `validate_provider_config(config)`: post-merge check that `api_base` and `token_env` are non-empty, delegates to `validate_api_base` for URL shape
- All return `Error::InvalidConfig` with descriptive messages including the hostname/context
- Re-exported from `actup_core::{validate_hostname, validate_api_base, validate_provider_config}`
- 27 tests: 16 hostname (valid simple/subdomain/short/hyphens, rejects empty/uppercase/caps/https/http/path/port/leading-trailing-internal-whitespace/tab, context propagation), 7 api_base (valid https/http/path, strips trailing slashes, rejects empty/no-scheme/ftp/query/fragment, context propagation), 8 provider_config (valid github/ghe, rejects empty api_base/token_env/invalid api_base, host in error, query/fragment rejected)
- Files changed: `crates/core/src/config/validation.rs` (new), `crates/core/src/config/mod.rs`, `crates/core/src/lib.rs`
- **Learnings:** `Error::InvalidConfig.path` field works well as a generic context string (not just file paths). `validate_api_base` returns the normalized value rather than mutating — functional style fits better with the resolution pipeline where the caller will build `ProviderConfig`. `kind` validation (required after merge) is deferred to `effective_host()` in the resolution-logic task since it requires registration lookup.
